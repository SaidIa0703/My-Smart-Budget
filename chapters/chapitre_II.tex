\section{Objectifs métier, techniques et pédagogiques}

\subsection{Objectifs métier}

\textbf{My Smart Budget} répond à un besoin concret identifié auprès de plusieurs profils d'utilisateurs : de nombreux étudiants, jeunes actifs et familles peinent à suivre leurs dépenses quotidiennes et à planifier leurs budgets mensuels de manière efficace.

L'objectif métier principal est de \textbf{simplifier la gestion budgétaire personnelle} via une interface claire, automatisée et personnalisable, tout en offrant une vision en temps réel de la situation financière.

\subsection{Justification des exclusions (Won't Have v1)}

\begin{itemize}
  \item \textbf{Agrégation bancaire} : nécessite une certification PSD2 (6--12 mois), des coûts d'APIs élevés (Plaid/Budget Insight), et une maintenance complexe. Prévu en v2.0 après POC.
  \item \textbf{OCR} : taux d'erreur élevé sur les tickets français (formats variés), coût d'API externe (\$1.50/1000 requêtes). Réévaluation en v2.1.
  \item \textbf{IA de recommandations} : algorithmes de ML nécessitant un dataset de 1000+ utilisateurs sur 6 mois minimum. Prévu en v2.5.
\end{itemize}

\subsection{Critères d'acceptation détaillés (Definition of Done)}

\subsubsection{US-01 : Compte \& Connexion}

\paragraph{Critères fonctionnels}
\begin{enumerate}
  \item Formulaire d'inscription avec validations :
    \begin{itemize}
      \item Email unique (format RFC 5322)
      \item Mot de passe $\geq 12$ caractères (1 majuscule, 1 minuscule, 1 chiffre, 1 caractère spécial)
      \item Confirmation du mot de passe identique
    \end{itemize}
  \item Mot de passe haché avec bcrypt (cost factor $\geq 12$)
  \item Token JWT signé (HS256, expiration 24h, payload : userId + rôle)
  \item Redirection automatique vers \texttt{/dashboard} après connexion
  \item Mécanisme anti-brute-force : 3 tentatives $\rightarrow$ temporisation 5 min
\end{enumerate}

\paragraph{Critères techniques}
\begin{itemize}
  \item Tests unitaires : 5 cas (inscription OK, email doublon, mot de passe faible, JWT valide, JWT expiré)
  \item Tests E2E : parcours complet inscription $\rightarrow$ connexion $\rightarrow$ page protégée
  \item Latence de l'endpoint \texttt{/register} $< 800$ms (P95)
  \item Logs d'audit : tentatives échouées + IP (conservation 90j)
\end{itemize}

\paragraph{Critères d'acceptation mesurables}
\begin{itemize}
  \item[$\checkmark$] 100\,\% des connexions avec des identifiants valides réussissent
  \item[$\checkmark$] 0 token JWT accepté après expiration
  \item[$\checkmark$] Taux d'activation $\geq 80\,\%$ (compte créé $\rightarrow$ 1\textsuperscript{re} connexion dans les 7 jours)
\end{itemize}

\section{Architecture 3-tiers et Responsabilités}

\subsection{Vue d'ensemble (description textuelle)}

L'application suit une architecture \textbf{3-tiers classique} séparant les responsabilités :

\begin{itemize}
  \item \textbf{Client Web} (navigateur) : interface utilisateur interactive React, validation côté client, gestion du state local (Context API/Zustand).
  \item \textbf{API REST} (Express sur Node.js) : logique métier, authentification JWT, validation des entrées, orchestration des requêtes DB, rate limiting, logs structurés.
  \item \textbf{Base de données} (MongoDB) : persistance des données NoSQL, agrégations natives, index de performance, réplication automatique (MongoDB Atlas).
\end{itemize}

\textbf{Déploiement} : conteneurs Docker orchestrés via Docker Compose (v1). CI/CD via GitHub Actions (tests automatisés, build, déploiement sur Render/Vercel).

\textbf{Observabilité minimale (v1)} : journaux applicatifs centralisés (Winston $\rightarrow$ fichiers), métriques de performance (Lighthouse CI), monitoring d'uptime (UptimeRobot).

\subsection{Architecture logique (responsabilités détaillées)}

\subsubsection{Couche Présentation (Front-end)}

\begin{itemize}
  \item \textbf{Pages} : routage React Router v6 (\texttt{/auth}, \texttt{/dashboard}, \texttt{/transactions}, etc.)
  \item \textbf{Composants} : découpage atomique (Atomic Design) : atomes (boutons, inputs), molécules (formulaires), organismes (cartes de dashboard)
  \item \textbf{Validation UI} : React Hook Form + Yup (schémas partagés avec le back-end)
  \item \textbf{State management} : Zustand pour l'état global (utilisateur connecté, filtres actifs), Context API pour les thèmes
  \item \textbf{Accessibilité} : attributs ARIA, navigation clavier, contrastes WCAG 2.1 AA, tests avec axe-core
\end{itemize}

\subsubsection{Couche Métier (Back-end)}

\begin{itemize}
  \item \textbf{Routes Express} : architecture modulaire par domaine :
    \begin{itemize}
      \item \texttt{/auth} : inscription, connexion, stratégie JWT (Passport), refresh tokens (v2)
      \item \texttt{/users} : CRUD profils, gestion des rôles, suppression RGPD
      \item \texttt{/transactions} : CRUD transactions, filtres, agrégations (totaux par catégorie)
      \item \texttt{/budgets} : CRUD enveloppes, calcul du ``reste à vivre'', historiques
      \item \texttt{/categories} : CRUD catégories (globales + personnalisées)
      \item \texttt{/import} : parsing CSV, validation, détection de doublons, rapports
      \item \texttt{/export} : génération CSV/JSON, compression ZIP
    \end{itemize}
  \item \textbf{Services métier} : logique de calcul isolée (testable unitairement) :
    \begin{itemize}
      \item \texttt{BudgetCalculatorService} : calcul du reste à vivre, pourcentages de consommation des enveloppes
      \item \texttt{TransactionAggregatorService} : agrégations MongoDB (sommes par catégorie, évolutions mensuelles)
    \end{itemize}
  \item \textbf{Middlewares} : authentification JWT, contrôle d'accès par rôle, gestion globale des erreurs
  \item \textbf{Rate limiting} : Express-rate-limit (10 req/sec par IP, 100 req/min par utilisateur)
  \item \textbf{Logs} : Winston avec niveaux (error, warn, info, debug), rotation quotidienne, format JSON
\end{itemize}

\subsubsection{Couche Données (Base de données)}

\begin{itemize}
  \item \textbf{Schémas Mongoose} : modèles typés (User, Transaction, Budget, Category, AuditLog)
  \item \textbf{Relations} : références ObjectId avec \texttt{populate()} pour les jointures
  \item \textbf{Index de performance} :
    \begin{itemize}
      \item \texttt{db.transactions.createIndex(\{userId: 1, date: -1\})}
      \item \texttt{db.transactions.createIndex(\{categoryId: 1\})}
      \item \texttt{db.budgets.createIndex(\{userId: 1\})}
    \end{itemize}
  \item \textbf{Migrations} : scripts de migration versionnés (\texttt{migrate-mongo})
  \item \textbf{Seeds} : données de test (15 catégories prédéfinies, 2 utilisateurs démo, 50 transactions)
  \item \textbf{Sauvegardes} : backup automatique quotidien MongoDB Atlas (rétention 30j), restauration testée mensuellement
\end{itemize}

\subsection{Justifications détaillées (choix critiques)}

\subsubsection{MongoDB vs PostgreSQL}

\textbf{Pourquoi MongoDB ?}
\begin{itemize}
  \item \textbf{Flexibilité du schéma} : évolution rapide du modèle de données en phase MVP sans migrations complexes.
  \item \textbf{Agrégations natives} : pipeline d'agrégation MongoDB très performant pour les calculs budgétaires (sommes, moyennes, groupBy).
  \item \textbf{Scalabilité horizontale} : sharding natif pour la croissance future (10k+ utilisateurs).
  \item \textbf{Format JSON natif} : cohérence avec l'API REST et le front-end React (pas de mapping ORM).
  \item \textbf{MongoDB Atlas} : solution cloud managée avec backup automatique et monitoring inclus (tier gratuit 512MB).
\end{itemize}

\textbf{PostgreSQL écarté car} :
\begin{itemize}
  \item Schéma plus rigide nécessitant des migrations fréquentes en phase MVP.
  \item Setup plus complexe pour la réplication/sharding.
  \item Nécessite un ORM additionnel (TypeORM/Prisma) ajoutant de la complexité.
\end{itemize}
