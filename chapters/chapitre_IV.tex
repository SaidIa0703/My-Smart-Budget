\chapter{Conception fonctionnelle et technique}

\textbf{IMPORTANT :} Cette phase de conception est \textbf{CRUCIALE} et a été \textbf{COMPLÈTEMENT TERMINÉE} avant le démarrage du développement.  
Pour \textbf{App Budget V3}, j’ai construit une conception fonctionnelle et technique détaillée, validée itérativement, qui sert de référence unique au développement, aux tests et à la soutenance.

\textbf{Mon approche de conception :}  
La conception d’\textbf{App Budget V3} s’est déroulée en plusieurs étapes structurées :

\begin{itemize}
    \item \textbf{1. Cadrage fonctionnel} : à partir des objectifs SMART et des personae (\textit{Léa} et \textit{Marc}), j’ai identifié les besoins critiques (suivi des transactions, enveloppes, dashboard, import/export).
    \item \textbf{2. Modélisation des Use Cases} : j’ai listé et priorisé les cas d’usage du point de vue utilisateur, puis je les ai regroupés en Epics et User Stories (MoSCoW) sur GitHub.
    \item \textbf{3. Diagrammes UML} : j’ai conçu un \textbf{diagramme de cas d’utilisation}, un \textbf{diagramme de classes détaillé}, puis des \textbf{diagrammes de séquence} pour les flux critiques (authentification, création de transaction, import CSV, consultation dashboard).
    \item \textbf{4. Conception UI/UX} : j’ai réalisé le \textbf{zoning}, les \textbf{wireframes} puis les \textbf{maquettes Figma} haute fidélité pour les pages principales : connexion, dashboard, transactions, enveloppes, import, profil.
    \item \textbf{5. Modélisation des données} : j’ai construit un \textbf{MCD → MLD → MPD} pour la base PostgreSQL, en alignant les entités sur le modèle objet Prisma.
    \item \textbf{6. Architecture 3 tiers} : j’ai formalisé l’architecture \textbf{Next.js 14 (front)} + \textbf{NestJS 10 (API)} + \textbf{PostgreSQL 15 (données)}, conteneurisée avec Docker.
    \item \textbf{7. Plan de tests} : chaque User Story a été enrichie avec des \textbf{critères d’acceptation} et un \textbf{plan de tests} (unitaires, E2E Playwright, tests utilisateurs).
    \item \textbf{8. Validation} : la conception a été relue et validée avant toute implémentation, ce qui m’a évité de lourdes refactorisations pendant le développement.
\end{itemize}

\begin{conseil}
\textbf{Pourquoi la conception est-elle si importante dans App Budget V3 ?}
\begin{itemize}
    \item \textbf{Évite les refactorisations coûteuses} : le modèle de données (enveloppes, transactions, catégories) a été figé avant le développement, ce qui m’a évité de casser l’API au milieu du projet.
    \item \textbf{Guide le développement} : chaque User Story est tracée vers un Use Case, un diagramme de séquence et un schéma de base de données.
    \item \textbf{Facilite les tests} : les flux UML (ex : ajout de transaction, import CSV) ont servi de base aux scénarios Playwright et aux tests utilisateurs.
    \item \textbf{Réduit les risques} : les cas d’erreur (CSV invalide, dépassement de budget, échec d’authentification) ont été anticipés dans les séquences.
    \item \textbf{Améliore la communication} : la conception est partagée sur GitHub (\texttt{/docs}) et supporte la démonstration lors de la soutenance CDA.
\end{itemize}

\section{Diagrammes de séquence}

Les diagrammes de séquence précisent, pour chaque cas d’usage critique, \textbf{l’enchaînement des appels} entre :

\begin{itemize}
    \item le \textbf{client Next.js 14} (frontend),
    \item l’\textbf{API NestJS 10} (backend),
    \item la \textbf{base PostgreSQL 15} (via Prisma 5),
    \item et, en v2.0, les \textbf{services externes} (emails, notifications).
\end{itemize}

Ils servent de référence pour l’architecture des contrôleurs / services NestJS, pour la signature des endpoints et pour les tests d’intégration.

\subsection{Séquence 1 : Authentification (US-01)}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{assets/images/seq-auth-login.png}
    \caption{Diagramme de séquence -- Connexion utilisateur}
    \label{fig:seq-auth-login}
\end{figure}

\textbf{Description du flux nominal :}
\begin{enumerate}
    \item L’utilisateur saisit ses identifiants sur la page \texttt{/auth/login} (Next.js).
    \item Le frontend envoie une requête \texttt{POST /auth/login} à l’API NestJS.
    \item Le \texttt{AuthController} appelle le \texttt{AuthService} qui :
    \begin{itemize}
        \item vérifie l’email et le mot de passe (bcrypt),
        \item génère un JWT (HS256, exp 24h),
        \item journalise la tentative de connexion.
    \end{itemize}
    \item L’API renvoie un \texttt{200 OK} avec le token et les informations de base de l’utilisateur.
    \item Le frontend stocke le token (cookie HTTPOnly) et redirige l’utilisateur vers \texttt{/dashboard}.
\end{enumerate}

\textbf{Gestion d’erreur :}  
En cas de mot de passe incorrect ou d’utilisateur inexistant, l’API renvoie un \texttt{401 Unauthorized} et le frontend affiche un message d’erreur sans divulguer d’information sensible.

\subsection{Séquence 2 : Création d’une transaction (US-03)}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{assets/images/seq-create-transaction.png}
    \caption{Diagramme de séquence -- Création d’une transaction}
    \label{fig:seq-create-transaction}
\end{figure}

\textbf{Flux nominal :}
\begin{enumerate}
    \item L’utilisateur clique sur “Ajouter une transaction” sur la page \texttt{/transactions}.
    \item Le frontend valide les champs côté client (Zod) puis appelle \texttt{POST /transactions}.
    \item Le \texttt{TransactionsController} injecte \texttt{TransactionsService} et appelle \texttt{create()}.
    \item Le service valide les données côté backend, associe la transaction au \texttt{userId} du token, puis appelle Prisma.
    \item Prisma exécute un \texttt{INSERT} dans la table \texttt{transactions}.
    \item L’API renvoie la transaction créée, le frontend met à jour la liste et les totaux.
\end{enumerate}

\textbf{Gestion d’erreur :}
\begin{itemize}
    \item Montant invalide ou date dans le futur : retour \texttt{400 Bad Request}.
    \item Catégorie inexistante ou non liée à l’utilisateur : retour \texttt{404 Not Found}.
\end{itemize}

\subsection{Séquence 3 : Déclenchement d’une alerte de budget (US-07, v2.0)}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{assets/images/seq-budget-alert.png}
    \caption{Diagramme de séquence -- Déclenchement d’une alerte de budget}
    \label{fig:seq-budget-alert}
\end{figure}

\textbf{Flux nominal :}
\begin{enumerate}
    \item Un \textbf{cron job} planifié déclenche périodiquement le \texttt{BudgetAlertsService}.
    \item Le service interroge PostgreSQL (via Prisma) pour récupérer les enveloppes et les montants consommés.
    \item Pour chaque enveloppe, le service calcule le pourcentage consommé.
    \item Si un seuil (70\,\%, 90\,\%, 100\,\%) est franchi, une \texttt{Notification} est créée en base.
    \item Un service d’envoi (email / push) en v2.0 envoie l’alerte à l’utilisateur.
\end{enumerate}

\begin{conseil}
\begin{itemize}
    \item J’ai modélisé en priorité les séquences pour : Auth (US-01), Transactions (US-03), Enveloppes (US-04), Import CSV (US-05) et Alertes (US-07).
    \item Les séquences détaillent toujours le \textbf{flux nominal} et au moins un \textbf{flux d’erreur} (ex : CSV invalide, dépassement de plafond, erreur DB).
\end{itemize}
\end{conseil}

\section{Conception de base de données}

Pour App Budget V3, j’ai choisi \textbf{PostgreSQL 15} comme base de données unique pour la v1.0, avec Prisma 5 comme ORM.  
Le modèle de données suit la démarche \textbf{Merise} :

\begin{itemize}
    \item MCD : entités métier (User, Transaction, Category, BudgetEnvelope, Notification, ImportJob).
    \item MLD : tables relationnelles, clés primaires / étrangères.
    \item MPD : implémentation PostgreSQL avec contraintes et index.
\end{itemize}

\subsection{MCD (Modèle Conceptuel de Données)}

Les principales entités sont :

\begin{itemize}
    \item \textbf{Utilisateur} : identifiants, préférences, rôle.
    \item \textbf{Catégorie} : \textit{Alimentation, Logement, Loisirs}, etc.
    \item \textbf{Transaction} : opération financière (date, montant, type, catégorie).
    \item \textbf{EnveloppeBudgétaire} : plafond par période et catégories associées.
    \item \textbf{Notification} (v2) : alertes sur dépassement de seuil.
    \item \textbf{ImportJob} : journalisation des imports CSV.
\end{itemize}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.95\textwidth]{assets/images/mcd-app-budget-v3.png}
    \caption{MCD -- App Budget V3 (Merise)}
    \label{fig:mcd-app-budget-v3}
\end{figure}

\subsection{MLD (Modèle Logique de Données)}

Traduction en tables relationnelles :

\begin{itemize}
    \item \texttt{users(id, email, password\_hash, role, currency, locale, created\_at, updated\_at)}
    \item \texttt{categories(id, name, type, user\_id NULL, created\_at)}
    \item \texttt{transactions(id, user\_id, category\_id, date, amount, type, label, created\_at)}
    \item \texttt{budget\_envelopes(id, user\_id, name, monthly\_limit, created\_at)}
    \item \texttt{envelope\_categories(envelope\_id, category\_id)}
    \item \texttt{notifications(id, user\_id, envelope\_id, type, message, read\_at, created\_at)}
    \item \texttt{import\_jobs(id, user\_id, filename, rows\_ok, rows\_ko, created\_at)}
\end{itemize}

\subsection{MPD (Modèle Physique de Données)}

Exemple de définition SQL simplifiée :

\begin{lstlisting}[language=SQL]
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  role TEXT NOT NULL DEFAULT 'USER',
  currency TEXT NOT NULL DEFAULT 'EUR',
  locale TEXT NOT NULL DEFAULT 'fr-FR',
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE categories (
  id SERIAL PRIMARY KEY,
  name TEXT NOT NULL,
  type TEXT NOT NULL, -- EXPENSE / INCOME
  user_id INTEGER REFERENCES users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE transactions (
  id SERIAL PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  category_id INTEGER NOT NULL REFERENCES categories(id),
  date DATE NOT NULL,
  amount NUMERIC(12,2) NOT NULL,
  type TEXT NOT NULL CHECK (type IN ('DEBIT','CREDIT')),
  label TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_transactions_user_date
  ON transactions(user_id, date DESC);

CREATE TABLE budget_envelopes (
  id SERIAL PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  monthly_limit NUMERIC(12,2) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE envelope_categories (
  envelope_id INTEGER NOT NULL REFERENCES budget_envelopes(id) ON DELETE CASCADE,
  category_id INTEGER NOT NULL REFERENCES categories(id) ON DELETE CASCADE,
  PRIMARY KEY (envelope_id, category_id)
);
\end{lstlisting}

\begin{conseil}
\begin{itemize}
    \item Tous les schémas sont gérés par \textbf{Prisma Migrate} (\texttt{schema.prisma} versionné dans Git).
    \item Des index ciblés ont été ajoutés sur \texttt{(user\_id, date)} et \texttt{(user\_id, category\_id)} pour optimiser le dashboard et les filtres.
\end{itemize}
\end{conseil}

\section{Architecture 3 tiers}

App Budget V3 adopte une architecture 3 tiers classique, adaptée à une application web moderne :

\begin{itemize}
    \item \textbf{Tier 1 -- Présentation} : \textbf{Next.js 14} (React 18, TypeScript, Tailwind CSS).
    \item \textbf{Tier 2 -- Logique métier} : \textbf{NestJS 10} (Node.js 20, API REST, validation, auth JWT).
    \item \textbf{Tier 3 -- Données} : \textbf{PostgreSQL 15} (via Prisma 5).
\end{itemize}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\textwidth]{assets/images/arch-3tiers-app-budget-v3.png}
    \caption{Architecture 3 tiers -- App Budget V3}
    \label{fig:arch-3tiers-app-budget-v3}
\end{figure}

\subsection*{Tier 1 : Présentation (Next.js 14)}

\begin{itemize}
    \item Routing par pages : \texttt{/auth}, \texttt{/dashboard}, \texttt{/transactions}, \texttt{/envelopes}, \texttt{/import}, \texttt{/profile}.
    \item State management léger avec \textbf{Zustand} (filtres, session).
    \item Formulaires gérés avec \textbf{React Hook Form + Zod}.
    \item Requêtes HTTP via \texttt{fetch} / \texttt{axios} vers l’API NestJS.
\end{itemize}

\subsection*{Tier 2 : Logique métier (NestJS 10)}

\begin{itemize}
    \item Modules découpés par domaine : \texttt{AuthModule}, \texttt{UsersModule}, \texttt{TransactionsModule}, \texttt{BudgetsModule}, \texttt{ImportModule}, \texttt{AnalyticsModule}.
    \item Authentification JWT via \textbf{Passport} et \textbf{Guards NestJS}.
    \item Validation de toutes les entrées via \textbf{class-validator}.
    \item Documentation de l’API via \textbf{Swagger}.
\end{itemize}

\subsection*{Tier 3 : Données (PostgreSQL 15)}

\begin{itemize}
    \item Toutes les opérations de lecture/écriture passent par Prisma.
    \item Sauvegardes régulières via \texttt{pg\_dump}.
    \item Stratégie de migrations contrôlée par \texttt{prisma migrate}.
\end{itemize}

\begin{conseil}
\begin{itemize}
    \item L’API est \textbf{stateless}, ce qui permettra à terme de scaler horizontalement (plusieurs instances NestJS derrière un reverse proxy).
    \item Le découpage modulaire NestJS facilite les tests unitaires et l’évolution (ajout de modules \texttt{NotificationsModule}, \texttt{AdminModule} en v2.0).
\end{itemize}
\end{conseil}

\section{Cohérence globale UML, API, services, base et interface}

Une exigence forte du jury CDA est la \textbf{cohérence} entre :

\begin{itemize}
    \item la \textbf{conception UML} (Use Cases, classes, séquences),
    \item les \textbf{endpoints d’API} NestJS,
    \item les \textbf{services métiers},
    \item le \textbf{schéma de base de données} PostgreSQL,
    \item et l’\textbf{interface utilisateur} Next.js.
\end{itemize}

Le tableau suivant résume cette traçabilité pour quelques fonctionnalités clés :

\begin{center}
\begin{tabular}{|p{2.5cm}|p{2.5cm}|p{3cm}|p{3cm}|p{3cm}|}

\textbf{Use Case} & \textbf{Classe UML} & \textbf{Endpoint API} & \textbf{Table / Modèle} & \textbf{Écran UI} \\

\begin{tcolorbox}[colback=green!5!white,colframe=green!60!black,title=\textbf{Traçabilité complète pour UC02 -- Transactions}]

\begin{itemize}
    \item \textbf{Use Case} : UC02 -- Gérer ses transactions (ajouter / modifier / supprimer).
    \item \textbf{User Story} : US-03 \og En tant qu’utilisateur, je peux créer des transactions afin de suivre mes dépenses et revenus \fg{}.
    \item \textbf{Classe UML} : \texttt{Transaction} (diagramme de classes).
    \item \textbf{Séquence UML} : \textit{Séquence 2 -- Création d’une transaction} (figure~\ref{fig:seq-create-transaction}).
    \item \textbf{Endpoint API} : \texttt{POST /transactions}, \texttt{PATCH /transactions/:id}, \texttt{DELETE /transactions/:id}.
    \item \textbf{Modèle Prisma} : \texttt{model Transaction \{ ... \}}.
    \item \textbf{Tables} : \texttt{transactions}, \texttt{categories}, \texttt{users}.
    \item \textbf{Écran UI} : page \texttt{/transactions}, formulaire \og Ajouter une transaction \fg{}.
\end{itemize}

Cette traçabilité montre que la \textbf{conception UML n’est pas théorique}, mais bien utilisée comme fondation pour l’API, la base de données et l’interface.
